HOW IT WORKS · 01

The agent OS

Most of what I have built runs on one thing: a shared memory every agent reads and writes, a crew of named workers that run on schedules whether I am at the desk or not, and a phone that can pick up any session mid-thought. This is how that actually works — including the parts that break.

DESIGNED, BUILT AND RUN BY ONE PERSON · RUNNING DAILY

01 · WHAT IT IS

A crew, not a chatbot.

The difference that matters is standing work. A chat assistant answers when spoken to and forgets. This is a set of named agents with jobs, schedules, and a shared place to put what they learn — the Ingester reads whatever lands in the inbox, the Harvester turns long video into briefings (and can analyze motion for shot lists with a Visuals lens), the Sentinel watches for changes worth knowing about, RICO drafts in my voice, and so on.

They are not separate products bolted together. They are separate workers pointed at one memory. That single decision is what makes the whole thing behave like an operating system instead of a folder of scripts.

02 · THE MEMORY

One source of truth, or it does not work.

The vault is a structured markdown knowledge base backed by a database with semantic search. Project pages, decisions, session logs, methodology. Agents read it before they act and write to it after, which means I never re-explain context and no two agents hold different versions of the same fact.

It is exposed to any AI assistant over the Model Context Protocol, so the same memory is reachable from a terminal, a browser, or a phone without a bespoke integration per surface. The unglamorous half is discipline: one page per project that is rewritten rather than appended, so retrieval ranks current state above history.

INFRA 01 · THE BRAIN

One memory. Every agent.

A knowledge vault the whole crew reads and writes — decisions, project state, hard-won lessons. Nothing gets re-explained. A session ends; the memory doesn't.

INFRA 02 · THE PULSE

It thinks while the computer is off.

A market data engine recomputes the entire US market every night in the cloud — end to end, unattended. The platforms above wake up already knowing.

03 · THE INTAKE LINE

Drop anything in one inbox.

Notes, PDFs, images, audio, video. A sorter classifies each file to a project, extracts its text, renders a thumbnail, and files it — writing one row to a shared events table so every surface can show the same history.

The interesting case is a scan with no text layer, which used to be detected as unreadable and filed with an empty extract anyway — the worst kind of failure, because it looks like success. Now, when text extraction returns under about forty characters, the page is rasterised and passed to a vision model instead. Roughly eighteen seconds, and no metered spend.

04 · THE PART I AM PROUDEST OF

Two engines. One contract.

There are two separate processors. One runs on my workstation and handles everything while the machine is on. The other runs in the cloud on a schedule, for when it is not. They are built differently, they have different front doors, and they use different brains.

They write the same events table, in the same shape. That is the whole trick: because the output contract is identical, every surface downstream is indifferent to which engine did the work, and either can be worked on or taken offline without touching the other. When something looks wrong, the first diagnostic question is simply which engine produced the row.

05 · COST

Free by construction, not by discipline.

This runs at effectively no marginal cost, and that is an architectural property rather than a habit. The default brain is a local CLI covered by a flat-rate subscription, behind it a chain of fallbacks, and at the end of the chain a model running on the workstation itself.

The safeguard that actually holds is a hard flag that makes metered APIs unreachable by construction — not merely discouraged, not a warning in a README. Kill switches for each provider live in the settings screen. The rule I enforce above all others is that exactly one automatic brain may be armed at a time, because two live paths means paying twice for the same work.

06 · HONESTLY

What breaks.

Every system like this has sharp edges, and a page that hides them is marketing. These are the current ones:

  • Cloud storage is the weak dependency. The file front door sits on a sync client that died twice in fourteen hours. Both times the process was simply gone. Nothing watched it, and a watchdog is the top of the backlog.
  • A verifier that cannot tell two failures apart. When it checks that a page was written, an unreachable drive and a file that was never created return the same empty answer — so an outage reads as though the model lied. The outcome is safe; the report is misleading.
  • One health probe covers two ingresses. A break in the unwatched one would go unnoticed. Not yet observed, which is not the same as fixed.
  • The classifier's project list is thin. Documents about newer projects get a weak guess, because the hint list has not kept up with what I have built.
  • The file store has no undo. It is not version-controlled, so bulk writes are snapshotted first. That is a procedure, and procedures are weaker than mechanisms.

Most of these share a shape worth naming: the system is good at doing the work and worse at knowing when it did not. That is where the next round of effort goes.
